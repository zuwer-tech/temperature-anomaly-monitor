# Итоговый технический отчёт

## Краткое резюме

`temperature-anomaly-monitor` — учебный прототип раннего обнаружения
необычного поведения температурных датчиков. Система сочетает объяснимые
инженерные правила и Isolation Forest, показывает качество входной пробы,
группирует отдельные тревожные точки в события и формирует операторский журнал.

Ключевой принцип проекта — **не обучать модель на файле, который сейчас
анализируется**. Режим `rules-only` работает без ML-артефактов, а
`rules+ML` использует только заранее обученный и проверенный комплект модели.

Проект демонстрирует инженерный ML-пайплайн, но не является сертифицированной
системой промышленной, химической, радиационной или ядерной безопасности.

## 1. Задача и назначение

Цель — помочь оператору заметить температурные отклонения раньше, чем просмотр
сырых рядов вручную. Система должна отвечать на четыре вопроса:

1. Достаточно ли качественны входные данные?
2. Есть ли необычная точка или последовательность точек?
3. Почему сформирована тревога?
4. Какое событие и какой датчик требуют проверки?

Это аналог лабораторного контроля: сначала проверяется пригодность пробы, затем
применяются известные реакции-правила, после чего ML ищет нетипичное сочетание
признаков. Решение оператора остаётся внешним по отношению к прототипу.

## 2. Данные

### 2.1. Каноническая схема

Пользовательский CSV должен содержать:

| Поле | Смысл |
|---|---|
| `timestamp` | корректные дата и время измерения |
| `sensor_id` | непустой идентификатор датчика |
| `temperature` | числовая температура, допускается `NaN` как потеря сигнала |
| `scenario` | необязательная учебная разметка |

Перед детекцией `data_quality.py` считает число строк и датчиков, пропуски,
дубли, полностью пустые каналы и переходы назад по времени. Сводка read-only:
она не исправляет и не маскирует исходную пробу.

### 2.2. Синтетический benchmark

`Data.py` создаёт 2 880 строк: шесть датчиков, восемь часов, шаг одна минута.
Размечены штатный режим и семь типов отклонений: резкий скачок, медленный
перегрев, дрейф, зависание, сильный шум, потеря сигнала и коррелированный рост.
Положительный класс оценки задан явно: `scenario != "normal"`.

### 2.3. Реальные данные

`Т2.csv` содержит около 5 400 точек одного датчика за примерно 1,5 часа в
диапазоне 49–109 °C. Формат `time_s, temp_C` преобразуется адаптером
`data_adapters.load_t2()`. Эти данные полезны для проверки инженерной
реалистичности, но не имеют независимой разметки всех аномалий и поэтому не
заменяют полноценный производственный validation-набор.

## 3. Архитектура

```text
CSV
 ├─ data_quality.py       паспорт входной пробы
 └─ preprocessing.py      проверка, сортировка, временные и статистические признаки
          │
          ├─ rule_config.py    единые пороги правил
          ├─ model_schema.py   единый порядок ML-признаков
          ▼
 anomaly_detection.py     rules-only или rules+ML
          │
          ├─ events.py         группировка тревог в события
          ├─ evaluation.py     независимые метрики и задержка
          └─ app.py            Streamlit-дашборд
```

Разделение ответственности уменьшает риск скрытых расхождений: правила имеют
одну конфигурацию, обучение и инференс используют одну ML-схему, а UI не
обучает модель.

## 4. Методы обнаружения

### 4.1. Предобработка и признаки

Строки стабильно сортируются по датчику и времени. Рассчитываются пропуски,
заполненная температура внутри канала, rolling mean/std, локальный z-score,
разность температур, физическая скорость °C/мин, зависание и отклонение от
группы. Полностью пустой канал остаётся пустым и не превращается в 0 °C.

Скользящие вычисления используют текущие и прошлые точки. Будущие значения не
попадают в признаки ранних строк.

### 4.2. Инженерные правила

| Правило | Текущий критерий | Базовый уровень |
|---|---|---|
| Потеря сигнала | `is_missing == 1` | Medium |
| Резкий скачок | `abs(temp_rate_c_per_min) > 5` | High |
| Локальное отклонение | `abs_z_score > 3` | Warning |
| Зависание | не менее 10 точных повторов подряд | Medium |
| Отклонение от группы | более 8 °C | Warning |
| Устойчивый перегрев | наклон rolling mean выше 0,12 | Warning |

Для каждой точки сохраняются все `triggered_rules`, главная причина
`primary_reason` и число правил `rule_count`.

### 4.3. Isolation Forest

Isolation Forest обучается только на ранних штатных строках. Сохраняются
`scaler.joblib`, `iforest.joblib` и `model_meta.json`. Metadata содержит
состав признаков, сведения о split и калибровку score.

При анализе выполняются только `transform`, `predict` и
`decision_function`; evaluation также не вызывает `fit`. Отсутствующий
комплект даёт `ModelNotTrainedError`, несовместимый —
`ModelCompatibilityError`.

`anomaly_score_norm` — относительный балл относительно train-baseline. Он
**не является вероятностью аварии** и не должен интерпретироваться как
сертифицированная оценка риска.

### 4.4. Объединение и события

```text
final_anomaly = rule_anomaly OR iforest_anomaly
```

Соседние аномальные точки одного датчика объединяются в событие. Для события
сохраняются начало, конец, длительность, максимум температуры, причины,
максимальный уровень и рекомендация. Группировка не меняет исходные решения
детектора.

## 5. Обучение и независимая оценка

Для синтетического benchmark заранее зафиксированы две временные границы:

- train: 720 ранних строк `scenario == "normal"` до 14:00;
- validation: 720 строк с 14:00 до 16:00, включая 650 normal и 70 anomaly;
- test: 1 440 строк с 16:00, включая 930 normal и 510 anomaly;
- пары `sensor_id + timestamp` трёх частей не пересекаются.

Validation содержит ранние сценарии `high_noise`, `signal_loss` и
`sharp_jump`. Она служит рабочей контрольной пробой для выбора параметров и
признаков. Test содержит более поздние `slow_overheating`, `sensor_drift`,
`stuck_sensor` и `correlated_growth` и используется только в `final_report`.

Причинные rolling-признаки сначала рассчитываются на всей доступной прошлой
истории, затем применяются временные маски. Поэтому будущие test-значения не
могут изменить train или validation. До расчёта test фиксируются параметры
Isolation Forest, список признаков, пороги правил, калибровка score и разметка.
Evaluation не вызывает `fit`.

Metadata модели версии 4 хранит обе границы и размеры всех частей. Неверный
формат, перепутанный порядок границ или пустая часть блокируют обучение до
создания артефактов.

Это независимость по времени внутри одного синтетического процесса. Она не
является независимой производственной валидацией: для неё нужен отдельно
собранный и экспертно размеченный реальный набор.
## 6. Результаты

Validation — рабочая часть из 720 строк:

| Слой | Precision | Recall | F1 |
|---|---:|---:|---:|
| Правила | 0,6163 | 0,7571 | 0,6795 |
| Isolation Forest | 0,4602 | 0,7429 | 0,5683 |
| Правила + Isolation Forest | 0,4314 | 0,9429 | 0,5919 |

Финальный test — закрытая часть из 1 440 строк:

| Слой | Precision | Recall | F1 |
|---|---:|---:|---:|
| Правила | 0,9718 | 0,2706 | 0,4233 |
| Isolation Forest | 0,7288 | 0,5059 | 0,5972 |
| Правила + Isolation Forest | 0,7570 | 0,5863 | 0,6608 |

На validation объединённый слой находит почти все размеченные аномалии, но
даёт больше ложных тревог. На закрытом test правила очень точны, но пропускают
много нетипичных участков; Isolation Forest повышает полноту, а объединённый
слой достигает F1 0,6608. Разница ожидаема, потому что части содержат разные
сценарии. Test нельзя использовать для последующей подгонки без создания нового
закрытого набора.

Регрессионные минимумы качества не ослаблялись и продолжают проверяться на
полном post-train holdout со всеми семью сценариями. Успешный GitHub Actions
подтвердил 189 тестов: общее покрытие 60,33%, покрытие строк 59,7% и ветвлений
62,4%.

После настройки обработки реального `Т2.csv` доля ложных тревог в учебной
проверке снизилась примерно с 94% до 10%. Число показывает улучшение
конкретного набора, но не доказывает качество на других установках.
## 7. Ограничения

- Нет независимо собранной и экспертно размеченной производственной выборки.
- Пороги правил учебные и не утверждены технологическим регламентом.
- Score Isolation Forest не является вероятностью или физической мерой риска.
- Нет оценки неопределённости измерений, поверки датчиков и часовых поясов.
- Потоковый сбор, отказоустойчивость, роли доступа и аудит оператора не
  реализованы.
- Демо-данные и модельные артефакты требуют синхронного обновления после
  изменения правил или признаков.
- Высокий FP rate может вызвать усталость от тревог; нужен отдельный пилот и
  наблюдение за тревожной нагрузкой.
- Прототип не должен самостоятельно управлять оборудованием или защитами.

## 8. Воспроизводимость

```bash
pip install -r requirements.txt -r requirements-dev.txt
python Data.py
python preprocessing.py
python train_model.py
python anomaly_detection.py
python evaluation.py --output evaluation_report.json
python -m pytest -q
streamlit run app.py
```

Изменение `MODEL_FEATURE_COLUMNS` требует переобучения всего комплекта
модели. Изменение правил выполняется через `rule_config.py` и сопровождается
регрессионными тестами.

## 9. Направления развития

Ближайшее обязательное усиление — собрать отдельный реальный набор, который
эксперт разметит независимо от разработки модели. Только такая «контрольная
проба из другой лаборатории» позволит оценить переносимость правил и ML за
пределами синтетического benchmark.

Дальше полезны пилотная проверка тревожной нагрузки, потоковый анализ и
обоснованное добавление Docker, API или базы данных.
## Заключение

Проект прошёл путь от демонстрационного скрипта к проверяемому учебному
ML-пайплайну: вход валидируется, модель не обучается на анализируемой пробе,
оценка отделена по времени, тревоги объясняются и группируются в события.
Следующий уровень зрелости требует не усложнения алгоритма, а независимых
данных, экспертной валидации и проверки операторской нагрузки.
