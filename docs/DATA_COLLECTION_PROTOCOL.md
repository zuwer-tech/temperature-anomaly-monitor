# Протокол сбора независимых реальных данных

## Статус этой итерации

Этот документ и шаблоны подготавливают сбор. Они **не являются реальным
набором данных** и не доказывают производственное качество модели.

Сейчас отсутствуют:

- несколько независимо проведённых реальных экспериментов;
- экспертная разметка начала и конца событий;
- подтверждённые штатные интервалы;
- закрытый test, не использованный при настройке;
- подтверждённые лицензия и разрешение на публикацию.

`Т2.csv` полезен как проверка одного реального формата, но это один канал без
независимой разметки. Он не заменяет validation или untouched test.

## Почему протокол нужен до CSV

В лаборатории сначала утверждают отбор, маркировку и хранение проб, затем
принимают пробирки. Иначе нельзя доказать, что контрольную пробу не использовали
при настройке метода.

Единица независимости — **целый эксперимент** (`experiment_id`), а не строка
или датчик. Все датчики и события одного опыта принадлежат только одной части:
train, validation или test.

## Артефакты

Рекомендуемая структура в разрешённом хранилище:

```text
real_dataset/
  manifest.json
  measurements/<experiment_id>.csv
  labels/events.csv
```

В GitHub сейчас добавляются только:

- `docs/schemas/real_data_manifest.schema.json`;
- `docs/templates/real_data_manifest.template.json`;
- `docs/templates/event_labels.template.csv`;
- тесты структуры документации.

Сырые промышленные данные нельзя добавлять в GitHub без письменного разрешения.

## 1. Паспорт набора и эксперимента

Manifest имеет версию и SHA-256 каждого файла. Для набора обязательны:

| Поле | Смысл |
|---|---|
| `dataset_id`, `dataset_version` | стабильное имя и версия |
| `created_at` | время создания manifest в UTC |
| `owner_role` | ответственная роль без лишних персональных данных |
| `license` | условия использования |
| `publication_permission` | разрешение на публикацию |
| `split_policy` | способ и момент фиксации разделения |
| `experiments` | паспорта опытов |

Для каждого эксперимента фиксируются:

- уникальный `experiment_id` и `split`;
- источник, установка, оборудование или процесс;
- путь и SHA-256 файла измерений;
- исходная схема и название адаптера;
- датчики, единицы и частота измерений;
- начало, конец и часовой пояс;
- описание штатного режима и контролируемых событий;
- роль эксперта и статус проверки разметки;
- пропуски, обслуживание и смены режима;
- происхождение и класс доступа.

Вместо ФИО и контактов достаточно роли и обезличенного идентификатора, если
этого хватает для воспроизводимости.

## 2. Измерения

Предпочтительный канонический CSV:

```csv
timestamp,sensor_id,temperature,temperature_unit,sensor_accuracy,quality_flag
```

Минимум: `timestamp`, `sensor_id` и `temperature`. Время хранится в ISO 8601,
а часовой пояс явно записывается. Температура остаётся исходным измерением без
скрытого сглаживания.

Исходник хранится неизменным. Конверсия единиц, восстановление абсолютного
времени или назначение sensor_id выполняются версионируемым адаптером и
описываются в manifest.

Также фиксируются ожидаемая частота, паузы, пропуски, калибровка, обслуживание,
ручные воздействия и смены технологического режима.

## 3. Экспертная разметка

`event_labels.template.csv` хранит строку на событие. Неопределённость границ
не скрывается:

| Поле | Назначение |
|---|---|
| `start_time_earliest` / `start_time_latest` | интервал начала |
| `end_time_earliest` / `end_time_latest` | интервал окончания |
| `label_status` | `confirmed`, `uncertain` или `disputed` |
| `confidence` | `high`, `medium` или `low` |
| `expert_comment` | физическое объяснение |
| `evidence_reference` | журнал опыта или другое свидетельство |

При точной границе earliest и latest совпадают. Для события нескольких
датчиков sensor_id равен `*`. Тип события описывает физический факт, а не
ответ алгоритма. Ground truth нельзя менять после просмотра предсказаний ради
улучшения метрик.

Отсутствие метки **не означает normal**. В manifest эксперт указывает:

- `coverage = full_timeline` — проверена вся временная шкала;
- `coverage = event_only` — размечены только известные события;
- `coverage = partial` — просмотрена только часть опыта;
- `unlabeled_policy = unknown_exclude_from_metrics` — необозначенные интервалы
  имеют неизвестный класс и исключаются из основной оценки;
- `unlabeled_policy = confirmed_normal_outside_events` допустим только при
  `full_timeline` и явном подтверждении эксперта.

`uncertain` и `disputed` не превращаются автоматически ни в anomaly, ни в
normal. Их показывают отдельно или используют в анализе чувствительности.
Основные метрики считают на подтверждённых метках.
## 4. Train, validation и test

Разделение выполняется **по experiment_id**:

- train — подтверждённые штатные опыты для обучения baseline;
- validation — другие опыты для выбора признаков и параметров;
- test — отдельные опыты только для финального отчёта.

Запрещено делить строки или датчики одного опыта между частями, выбирать test
после просмотра результатов, обучать scaler/модель на validation/test и
исправлять метки test под ответ алгоритма.

`split_policy.frozen_at` фиксируется до финальной оценки. После открытия test
изменённая модель требует нового untouched test либо честного перевода прежнего
test в validation.

## 5. Проверки целостности

В этой итерации тесты проверяют schema, обязательные поля, безопасный
template-only manifest, разные experiment_id трёх частей, заголовок разметки и
ссылку из `docs/DATA.md`.

После появления разрешённых файлов валидатор обязан проверить:

1. соответствие JSON Schema;
2. уникальность experiment_id и один split на опыт;
3. наличие файлов и совпадение SHA-256;
4. timestamp, timezone, sensor_id и единицы;
5. ссылки событий на существующие опыты и датчики;
6. порядок earliest/latest и начала/конца;
7. только подтверждённый normal в train;
8. untouched-статус final test.

Фактический адаптер нельзя надёжно написать без реальной исходной схемы. Он
добавляется вместе с разрешённой обезличенной пробой или утверждённым fixture.

## 6. Приватность и лицензия

До переноса данных подтверждаются владелец, цель, лицензия, разрешённые места
хранения, срок удаления и возможность публикации. Проверяется наличие
коммерческой тайны, параметров установки и персональных данных.

`publication_permission = "no_publication"` — безопасное значение по умолчанию.
Отсутствие запрета не считается разрешением. Manifest можно публиковать
отдельно от измерений, если это разрешено.

Проект не управляет оборудованием или защитами автоматически; решение остаётся
за человеком.

## 7. Работа после получения данных

1. Скопировать manifest-шаблон и заменить все `REPLACE_*`.
2. Сохранить сырые файлы неизменными и вычислить SHA-256.
3. Разметить события до просмотра ответа модели.
4. По возможности провести вторую экспертную проверку.
5. Зафиксировать split и версию методики.
6. Добавить адаптер и валидатор фактического формата.
7. Обучать только на подтверждённом normal train.
8. Настраивать на validation.
9. Один раз сформировать отчёт на untouched test.
10. Записать версии кода, модели и manifest.

## Когда вся карточка станет Done

Документационная фаза завершается после слияния protocol, schema, templates и
тестов. Полная задача завершится только когда имеются минимум три независимых
реальных эксперимента, экспертные event labels, проверенное происхождение и
разрешения, разделение целыми опытами, untouched test и протестированный
адаптер фактического формата.
